## 4. Execution

- **Machine:** the maintainer's own Mac (Mac16,6, Apple M4 Max, 36 GiB, macOS 26.7.3 build 25G342, arm64), the
  runner on Python 3.12.12, sleep disabled (`pmset`), recorded in each campaign folder's `machine.json`. No paid run on
  CI. Cause: spec §2 A9 fixes the machine; one machine keeps the time line comparable.
- **Concurrency 1:** one runner per folder (a lock), one vens at a time; before each paid run the runner refuses to
  start while another `vens*` process runs. Cause: A9's time shares neither the machine nor the accounts.
- **Command:** `vens generate --llm openai|anthropic --config-file CONFIG --sbom-serial-number urn:uuid:0…01
  --debug-dir debug --attest REPORT vex.cdx.json` (`--attest` on both arms, maintainer 27/11), environment limited to
  `PATH`, `HOME`, `TZ=UTC`, the proxy's base URLs, the key and the model.
- **Cache regime** (spec §2 "The cache"): each run starts with empty local caches; no prewarming, no cache busting, no
  cooling wait. OpenAI's automatic prefix cache is shared by both arms in the one organisation, interleaved; vens sends
  no `cache_control`, so an Anthropic cache token breaks the profile and leaves that A9 cost line UNDETERMINED (reader).
  The cost line is reread with cached tokens priced as input; a state that differs reads UNDETERMINED. The time line
  prints each arm's cached share. Cause: the initial state is the same for both versions, and nothing is warmed on
  purpose.
- **Order:** repetition outermost. Units (a block, or a DIR pair with its members a, b and c) crossed with the models
  are ranked by `sha256("vens-kpi/1.0/v0.7.0-c2/order" ‖ seed ‖ repetition ‖ unit ‖ model)`, each part NUL-terminated,
  lowest first. The two arms run back to back on the same unit; the arm that leads alternates from one position to the
  next; a unit's members run back to back within each arm. Cause: stages hold whole repetitions; pairs compare runs
  close in time; each arm leads half the units.
- **Seeds**, each `sha256(domain NUL spec-1.0 sha256 hex)`:
  - order: domain `vens-kpi/1.0/v0.7.0-c2/order-seed` → `27ff904d78f2999c7e5cf5b3e7e7d21c42b0006eb8d10eeed5e501b3524a9dd9`;
  - bootstrap: `vens-kpi/1.0/v0.7.0-c2/bootstrap-seed` → `c0ea3b90796c3f314619af06c125592c2ea6b95a805d25369c9b1282d40e5b4c`;
  - calibration: `vens-kpi/1.0/v0.7.0-c2/calibration-seed` → `4e9c406bd9ffccb642abe4d519e1146056cc4b01a37c7a874ecbbcff7ab3b55d`.

  Cause: public and recomputable, fixed before any data or output, chosen by no one.
- **Repetitions:** 0 (the smoke), 1-2, 3, 4-5, then 6-8 for the extension.
- **Timeout:** 3600 s per run; past it the runner kills vens and the run is aborted (an A7 result, its cost kept, its
  time left out). Cause: a hang guard, several times a 100-CVE run's expected length (about 80 serial calls). For the
  completion gate such a run is an A7 result, not a gate failure, unless the canary fails right after it: then it is a
  device failure and takes the network path below. The request it leaves in flight is counted at its maximum in the
  ledger, and the usage gate lists it without failing on it.
- **Network canary:** before each paid run, a TCP and TLS handshake to `api.openai.com:443` and
  `api.anthropic.com:443`, no request. While it fails, the runner retries it every 30 s for up to 2 h, then halts as a
  device failure; a STOP still stops it. A failed run's single re-attempt starts only after the canary passes. Cause:
  a short network cut on the maintainer's Mac must not end the campaign, and nothing read changes: the waits fall
  between runs, and a re-attempt replaces its failed attempt.
- **Provider refusal:** a run that exits non-zero on its own (not killed) after any of these responses, as the proxy
  recorded them, is a provider refusal, a device failure and not an A7 result:
  - a 400 only when its parsed `error.type` or `error.code` equals `insufficient_quota`, or its `error.message`
    begins "You have reached your specified API usage limits." or "Your credit balance is too low": these fields only,
    generic occurrences of credit, quota or billing do not qualify, and other 400s keep the ordinary A7 path;
  - a 401 or a 403;
  - a 429, a 5xx or a 529 as the run's last provider response, so vens's own retries did not get past it.

  Answers the proxy writes itself (the spend guard, an unreachable upstream) are not the provider's. On a refusal the
  runner writes `PAUSE` and exits with code 6 before the next paid run, with a message for the maintainer; no gate
  runs, none fails. Nothing runs while `PAUSE` is there. The maintainer's resume (`sh run.sh resume DIR NOTE`, after
  asking him) keeps it as `PAUSE.cleared-<time>` and journals the note; the next run of the campaign gives the refused
  run F0's single re-attempt, after the STOP, other-vens, canary and dispatch checks. A device failure its re-attempt
  resolves fails no gate. A refusal on the re-attempt halts (code 5) and goes to the maintainer. Cause: the provider's
  refusal of the evaluator's account says nothing of vens and hits both arms alike (§0, 5); a refusal that persists is
  the maintainer's to settle, not the runner's.
- **A re-attempt on a sealed block** (the blocks A9 reads) runs both arms of its pair again, back to back, in their
  scheduled order, each as its single re-attempt: the partner that already ran is re-run as `<folder>-a2` with
  `re_attempt_of` and `pair_of` the run (journal `a9-pair-re-run`); one that has not run yet runs next as scheduled.
  The partner's replaced attempt is not read by A5, A6 or A9; its cost counts. It stays an observation of vens:
  every healthy superseded partner output remains subject to A7, A1, A2 and A8 deterministic checks, including outputs
  from an unfinished later stage. Blocking findings enter the frozen reader's vector and aggregation and persist in
  subsequent readings. A5 and A9 retain the selected attempts. In the reader, a replaced attempt that ended on a
  healthy device is superseded, not dropped (`records.load_all`): its checks run in every reading, A7's exit-0 omission
  and substitution checks included; a device failure's replaced attempt is dropped as before. The gate's mechanical
  check also runs on its folder (the reader's `check`, in a view of the campaign folder where it is its run's only
  attempt), and an A7 result or an A1, A2 or A8 violation in it is published and listed in the report with its arm.
  In a candidate's attempt its output enters the reader's deterministic lines like any candidate output (A7: the
  run's cell, `A7|<block>|<model>`; A1, A2, A8: `<axis>|all`): a violation keeps its line from reading better than
  FAILED, whatever the re-run gives, and the delivery decision reads that line as FAILED; an A7 result counts in its
  cell's printed targets, as any technical failure does. In an R attempt it caps no line: the reader reads no 100%
  line on R, replaced or not. A9 reads only the retained attempts of both arms: summing every attempt would charge the
  partner's run twice, for a re-run the evaluator causes; superseded attempts count in the ledger and the spend, and
  are published. When the partner has already used its re-attempt for a device failure of its own, the pair cannot
  run again whole: the runner halts for the maintainer, and a refusal then halts instead of pausing. A partner whose
  second attempt is this pair's re-run (`pair_of` the run in its `attempt.json`, journal `a9-pair-re-run`) has used
  nothing: after a stop or a halt between the two, the run still gets its single re-attempt, next. Cause: A9 compares
  the arms on runs close in time (Order, above).
- **A9's seconds** run from the wall-clock launch to the VEX's mtime and count only when the launch ≤ the mtime ≤ the
  wall-clock exit, all three on the wall clock; the monotonic time to exit is kept apart as `seconds_to_exit`. Cause:
  a slew keeps the three in order; only a step that breaks it voids the seconds (§0, 7).
- **Records per run:** `attempt.json` (written before vens starts), `vex.cdx.json`, `vex.attestation.cdx.json`,
  `debug/`, `vens.stderr` with every form of the key cut out, `a9.jsonl` (with the body of every non-2xx provider
  response, up to 4,096 characters), `a9.json`.

## 6. Control: go, stop, gates, verdict at the stage reached

- **Go:** a stage starts only on its `GO-stage-k` file, which the coordinator writes after asking the maintainer and
  after checking both accounts' limits against the stage's budget (§13). At each stage's start and end, one line to
  the maintainer: what was spent, what comes next. Cause: the maintainer's 26/11 rules (stages, the go at each one);
  campaign 1 met the Anthropic monthly usage limit mid-stage. No go is given for campaign 2 yet (§13).
- **Stop:** the word "stop" to the coordinator, or a `STOP` file in the campaign folder, both checked before every run;
  the run in progress finishes; a resume reruns nothing. Cause: the maintainer's 26/11 rule.
- **Pause:** a provider refusal pauses the campaign before the next paid run until the maintainer's resume (§4); it
  is no stop and no gate failure.
- **No idle time:** the next stage starts at the maintainer's go; nothing else waits. The calibration (§9) runs at the
  end of stage 3, at $0, between paid runs.
- **Technical gates**, after repetition 1 and at each stage's end, reading no verdict line and spending no alpha:

  | Check | Fails the gate when |
  |---|---|
  | completion | a scheduled run neither completed nor ended as an A7 result (a non-zero exit, or a run killed at its timeout with the canary passing right after; a provider refusal is a device failure, never an A7 result) |
  | usage | a forwarded request is not priced (`usd_not_measured`), the one a timeout kill left in flight excepted |

## 8. Lines and tests

- **Primary lines:** 71, from `python -m vread lines` on F0's structure (§14): A5 repetitions 6, guard 6, models 3;
  A9 cost 6, time 6; A6 noise 18, shift 12, pattern 12; A4 (V4) 2. The size stays 71 at every stage; an unavailable
  test stays with p = 1.
- **A5 and A6 noise:** d per CVE, cluster bootstrap over CVEs, **200,000 draws**, seed per line from the bootstrap
  seed and the line id, percentile interval two-sided at 1 − α_k (`inverted_cdf`); p = (1 + #{d* beyond the
  threshold}) / (1 + B), doubled; a line's p is the smaller of its failure and gain p. Corrected bound: the percentile
  bound at 1 − α_k / (m − rank + 1). Cause: 20,000 draws give p ≥ 1.0 × 10⁻⁴, above Holm's first threshold at stages 1
  and 2 (0.005 / 71 = 7.0 × 10⁻⁵), so no line could be decided there; 200,000 give 1.0 × 10⁻⁵.
- **A5 two-band** (repetitions and models lines): d₂ per CVE = the share of the line's comparison pairs (repetition
  pairs; cross-model pairs) two bands or more apart, candidate − R, same cluster bootstrap; its failure p joins the
  line's (§11 #1).
- **States:** a failure confirmed at the line's Holm level reads FAILED, whatever the gain's p; a confirmed gain reads
  PROGRESS ESTABLISHED only on a line that holds, otherwise UNDETERMINED.
- **A9:** ratio of means over paired run blocks, Fieller-t, df = pairs − 1, normal blocks assumed; an unbounded
  interval is UNDETERMINED.
- **A6 test (1):** the mean signed shift per CVE in the instructed direction, bootstrap over CVEs, **one-sided** in
  that direction: p = (1 + #{s* ≤ 0}) / (1 + B), one line per direction. Cause: each direction is its own test (spec
  §3 "once per direction"), and the one-sided test fires more readily, so it cannot help the candidate; its false
  alarms are calibrated.
- **A6 test (2):** the number of CVEs whose every planted repetition is strictly beyond the base's range, against the
  exact per-CVE permutation null, Poisson-binomial over CVEs.
- **A6 rubric (3):** §7.3, no alpha, blocks from the first output.

  output; stages 3 and 4: also test (2) (5 repetitions, then 8).
